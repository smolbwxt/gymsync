# Phase W — Watch Companion + HR Broadcast — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** the Apple Watch companion (whose-turn, tap-to-log, soundboard, ledger glance) and the ephemeral heart-rate broadcast with zone-colored pills on the Live roster.

**Architecture:** infrastructure-first (T1 target + CI — nothing else can be verified until CI builds watchOS), then the plumbing (T2 WatchConnectivity bridge + envelope), then the Watch surfaces (T3), then HR end-to-end (T4 backend/opt-in + T5 pipeline/pills). Spec: `docs/superpowers/specs/2026-07-19-watch-hr-design.md`; product law = master spec §6.5 + wire shape §5 + canvas Live frames — implementers read them directly.

**Tech Stack:** watchOS/SwiftUI (CI-only compile — now for TWO platforms), WatchConnectivity, HealthKit (Watch-side HR), Supabase Realtime broadcast, pgTAP for any migration.

## Global Constraints
- Swift compiles ONLY in CI; the Watch target's very existence must be CI-proven before any Watch feature work merges conceptually (T1 gates T2-T5).
- HR is EPHEMERAL: no persistence anywhere (no table, no bpm in logs), broadcast-only Realtime channel, 1 msg/5s/user throttle. Hard law.
- Permission discipline: HealthKit HR read requested ONLY on first share_heart_rate enable; no prompt on launch/install of the Watch app.
- The Watch never talks to Supabase — phone-mediated everything; Watch set-logs route through the phone's EXISTING submit path (incl. offline queue).
- Migrations append-only + pgTAP; citations; memberwise traps; commit-don't-push; catalog/deviations for new PHONE surfaces (Watch surfaces = device-QA + Phase D).
- Never `git add -A`.
