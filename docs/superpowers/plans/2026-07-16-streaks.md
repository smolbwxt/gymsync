# Phase S — Streaks + Session-Lifecycle Gaps — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** schedule-based streaks per the master spec's Flow 7 — with the two lifecycle gaps they depend on (no_show wiring, burpee settlement) closed first — plus streak pushes, Stats UI, and harness coverage.

**Architecture:** backend-first: (1) no_show cron/RPC in the 3d idiom, (2) settlement derived from penalty set_logs (Burpee-Ledger RPC extension), (3) `user_streaks`/`group_streaks` + trigger functions + pgTAP matrix, (4) push payload cases through the existing outbox, then (5) Stats UI + seed extension + captures. Product rules come verbatim from `docs/superpowers/specs/2026-06-28-gymsync-design.md` (§Streaks schema, Flow 6 lateness, Flow 7 lifecycle) — implementers read those sections, not summaries.

**Tech Stack:** Postgres (pg_cron, triggers, RLS) + pgTAP; TypeScript payloads (push-dispatcher); SwiftUI; parity harness.

## Global Constraints

- Master-spec fidelity: Flow 7's rules are law (scheduled-at-any-point; completed-with-your-ready increments; break = your next scheduled session hits `scheduled_for` with you `no_show` OR session `abandoned` without your check-in; ad-hoc solo lifts neutral; group streak = every invited participant ready; milestones 7/14/30/60/90/180/365; at-risk push 30 min before; break silent). Cite the spec lines in reports.
- Streak tables writable ONLY by trigger functions (RLS: no client INSERT/UPDATE/DELETE; reads per spec — owner+friends / members).
- Migrations append-only via `db push` (pooler creds in `.env.local`, never echoed); every migration ships pgTAP (positive + negative RLS is a merge blocker per repo doctrine); suite runs via `node scripts/run_pgtap.js` — report TRUE totals (files + assertions).
- Push work goes through the EXISTING outbox → `push-dispatcher` Edge Function (3d): new event kinds follow `supabase/functions/push-dispatcher/payloads.ts` conventions; crons follow `20260716000003_push_cron.sql`'s idiom. Deno tests per that function's existing test pattern.
- Swift CI-only; cite declarations; no plain-private stored props on cross-file View structs; commit-don't-push.
- Seed changes stay idempotent (second-run counts stable) and never touch `personal_records` deletes (insert-if-absent doctrine).
- Never `git add -A`.
