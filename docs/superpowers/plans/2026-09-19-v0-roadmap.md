# The march to version 0 — roadmap

Written 2026-09-19, after Phase C1 shipped (PR #79, TestFlight 1053). This file is the authority a plan
or a review cites when it says which milestone a piece of work serves. It is deliberately short: it names
milestones, exit criteria, cuts and open decisions. It does not design anything — plans do that.

## What v0 is

A gym partner that gets a lifter and their crew to show up and train well: check in, warm up, lift on
**one** session screen alone or together, Coach steering progression, a trainer able to run clients.

Two owner rules govern the whole arc:

1. **Function before design.** Functional phases carry no design rounds. The design backlog is spent
   once, in M4.
2. **A new controller session per PR or phase.** The ledger, this roadmap and the plan are the handoff.

## How to use this file

- **Every plan names the milestone it serves and that milestone's exit criterion**, in its header.
- **A finding that does not move a milestone goes to the docket**, not into the phase.
- **Ranking rule, when two things compete:** data integrity > a missing capability > ship-readiness >
  design.
- Reviewers may cite a milestone's exit criterion as grounds for a finding ("M1's exit requires every
  capability moved or retired with a written reason; this one vanished").

## The five milestones

Each milestone closes with a TestFlight build the owner trains on.

### M1 · One session body — *function*

- **C1 — done.** Ad-hoc solo runs in the one session body (`SessionLiveView`); swaps are durable and
  keyed by routine slot; progress is counted per slot; every page has an exit; logging with no signal is
  safe. Plan: `2026-09-19-group-session-phase-c-plan.md`. TestFlight 1053.
- **C2 — next.** Its task outline (C2-S1 … C2-S7) and the capability ledger live in the C1 plan, section
  "C2 — the outline". On top of that outline, C2 carries what C1's final review handed over:
  - a server-side **abandon** state. Never `complete()` a session row the lifter did not act on —
    completing fires the leaderboard recompute, pushes `leaderboard_passed` to *another* user and credits
    campaigns. Abandon also gives the warm-up an End and stops a stale ad-hoc row reading as live in
    `friends_live()` (which has no age bound today);
  - **disk persistence** for the rest window, the swap outbox and the routine (all three are in memory
    today, so a cold launch offline has no plan). See "The M1/M2 seam" below;
  - deletion of `WorkoutSessionView`, `WarmUpPhaseView`, `AppState.liveSoloSession` and
    `SoloResumeCursor`; frame 66 retires (FLOOR −1).
- **Small functional gaps that may ride along** if they cost a task or less: Coach's `cue` lever rendered,
  HR zones from birth year, the stale "Coach coming soon" tour copy. Together's interval editor waits on
  an owner decision (below).

**Exit:** exactly one warm-up screen and one logging screen exist. Every capability the old solo screen
had is moved, or retired with a written reason in the capability ledger.

### M2 · Trust the data — *function*

- Disk persistence (if C2 did not land it — see the seam).
- Repair of sessions that were already double-logged. Needs the owner's word; a read-only count comes

- The parked Start crash (docket #6). The owner owes a repro or a log from build 824 or later.
- The Watch receives notifications (it has no notification code today).
- Push delivery verified end to end.

**Exit:** the owner, on their own device, finishes a full workout in airplane mode, killed and relaunched
mid-rest, and every set is counted exactly once.

### M3 · Ship-readiness — *switches, not builds*

- Privacy manifest (absent; verifying it needs a real archive build).
- Paywall flip. StoreKit and `PaywallView` are built; `Monetization.paywallEnabled = false`. Blocked on
  the owner's App Store Connect products.

**Exit:** an archive that passes App Store validation.

### M4 · The design pass — *the one big design spend, once per screen*

Named by the owner:

- the You page and the Trainer page (both functionally complete per the 2026-09-19 audit);
- the PR-celebration retry — A and B were both rejected, so the first step is asking what missed;
- **no session page scrolls**;
- the style selector and the rack ask move to the warm-up;
- MINIMISE's placement and the End card's weight;
- frame 136's defect, and frames 151/152 retire (FLOOR −2).

Proof cards before merge; the owner picks by name.

**Exit:** every screen above has been through exactly one design round and the owner has picked.

### M5 · v0 close

**Exit:** the field-report docket is at zero P0/P1; the owner and their crew spend a week on one build
with no data-integrity report; release notes; the tag.

## The M1/M2 seam — disk persistence

Disk persistence is listed under both C2 and M2 on purpose. It is a data-integrity item (top of the
ranking rule) and it is coupled to C2-S1: the routine editor's `soloEditedList` is exactly the state that
is lost today. **The C2 plan decides**: if persisting the routine falls out of moving the editor, all
three stores land in C2; if it would push C2 past its leg budget, persistence opens M2 as its first task.
Either way M1's exit does not depend on it and M2's exit does.
