### Launch pre-load gap — investigation result (2026-09-04; report `.superpowers/sdd/2026-09-04-investigations/launch-preload-report.md`)
- The launch overlay waits for exactly four things: the `.task` of the four tab roots (HomeView.swift:117, SocialTabView.swift:322, TrainerTabView.swift:103, YouTabView.swift:89 — the only `beginLaunchFetch` call sites), held for a fixed 1.3 s brand moment plus up to 2.5 s (RootView.swift:78-86). Nothing below depth 0 registers and structurally cannot: a `navigationDestination`'s content is not instantiated until the push.
- Why the ledger is slow: `ProgramRepository.history()` has no cache — no repository in the app has one; all 44 are stateless enums — so it starts at tap time behind a guaranteed spinner, two taps deep, racing CoachHomeView's five sequential awaits (incl. a two-round-trip 1,300-row `ExerciseRepository.fetchAll()`), even though HomeView's launch refresh already ran the identical query via `ProgramToday` and discarded the rows.
- **Recommendation: repository-level in-memory stale-while-revalidate caches** keyed by user id, cleared in `AuthService.signOut()` beside the four existing clears. Blast radius: one small new file + a few lines in 3-6 repositories, zero view changes (hidden behind the existing enum API); collapses the double-fetch; lowers peak memory (the catalog is currently held by up to four live views); leaves the 2.5 s cap alone. Then a narrow `LaunchWarmup` TaskGroup for first-ever opens.
- Ruled out: extending `beginLaunchFetch` + raising the cap — cannot reach unmounted destinations without eagerly mounting ~20 screens (reopens the `.id`-pinned LobbyView re-prop bug class).
- Unknowns: whether the 2.5 s cap fires in practice (Social's three sequential awaits are the likely long pole); real ledger latency; memory cost of a cached catalog.
