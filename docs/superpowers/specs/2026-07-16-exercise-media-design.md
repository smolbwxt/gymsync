# Phase E — Exercise Demonstration Media + Library Expansion — Design

**Status:** approved decisions (user, 2026-07-16): hosting = mirror into Supabase Storage; expansion folded in (roadmap amendment).
**Source revised (user, 2026-07-16):** ExerciseDB failed the license gate (data is RapidAPI-subscription-gated; ToS prohibits re-hosting — see Task 3 report). New source: **free-exercise-db** (github.com/yuhonas/free-exercise-db) — **Unlicense/public domain**, ~800 exercises, 2 photos each (start/end position). Media model: mirror both JPEGs per exercise to `exercise-media/<slug>/0.jpg` + `<slug>/1.jpg`; `demo_video_url` stores the public URL of `0.jpg`; the app derives frame 1 by convention and animates the pair as a 2-frame loop (~1s/frame). GIF decoding is no longer needed — `GSGifView` becomes `GSDemoView` (two-frame alternator, static fallback when frame 1 is absent). The master spec itself named Free Exercise DB as the seeding source (§future considerations), so this also realigns with the original plan.
**Roadmap:** Phase E of `docs/superpowers/plans/2026-07-16-remaining-build-roadmap.md`.

## Goal

Every exercise in the catalog shows a demonstration GIF on Exercise Detail, and the catalog grows from 30 seeded exercises to a curated ~150–300 set (the master spec's v1 target) — one import pipeline delivers both.

## Decisions (locked)

- **Source:** ExerciseDB open dataset (11k+ exercises with GIFs, names, target muscles, equipment). The implementation task discovers the exact dataset access point (open-source repo `ExerciseDB/exercisedb-api` / its published dataset) and records it in the script header.
- **License gate (mandatory, before any mass download):** verify the dataset's license permits mirroring/redistribution of the GIFs in our own bucket. If it does not, STOP and fall back to the wger open dataset (user's stated alternative) — record the finding in the mapping file header either way. Do not mirror media whose license we haven't read.
- **Hosting:** one-time mirror into a public-read Supabase Storage bucket `exercise-media`; the app loads only from our bucket. No third-party runtime dependency, no hotlinking.
- **Column:** reuse the existing `exercises.demo_video_url` (present since migration `20260709000002`) to store the bucket URL. No new column.
- **Expansion:** curated, not algorithmic — a checked-in, human-reviewable pack (`scripts/exercise_packs/expansion_v1.json`, same spirit as `routine_packs/`) listing the new exercises (slug, name, category, primary/secondary muscles, equipment, ExerciseDB match key). Coverage rule: all major muscle groups × common equipment (barbell, dumbbell, cable, machine, bodyweight), compound + isolation, capped ≈200 total.

## Components

### 1. Storage bucket migration
`exercise-media` bucket: public read, write restricted to service role. Follow the existing bucket-creation precedent in `supabase/migrations/20260711000002_storage_buckets.sql`.

### 2. Import script — `scripts/import_exercise_media.js`
Same `.env.local` service-key pattern as `seed_qa_fixtures.js`. Two idempotent passes in one run:
1. **Expand:** upsert `exercises` rows from the expansion pack (skip existing slugs — never mutate the seeded 30's identity fields).
2. **Media backfill:** for every `exercises` row with `demo_video_url IS NULL`, resolve its ExerciseDB match (explicit match key from the pack for new rows; a `scripts/exercise_media_map.json` mapping file for the original 30, generated by name/equipment/muscle matching and hand-reviewable), download the GIF once, upload to `exercise-media/<slug>.gif`, write `demo_video_url`. Rows already populated are skipped (idempotent); unmatched rows are listed loudly at the end, never guessed.

Progress logging per row (long-running download loop). Exit non-zero if the license gate was not recorded.

### 3. iOS — `GSGifView`
SwiftUI has no native animated-GIF view. Implement `GSGifView(url:)` decoding via `CGImageSource` (frame images + per-frame delay from GIF properties), animated with `TimelineView`/`CADisplayLink`-equivalent; loads via `URLSession` with `URLCache` so repeat views don't re-download; shows the existing photo-glyph placeholder while loading or when `demo_video_url` is nil. No third-party dependency.

### 4. Exercise Detail integration
Render the GIF card at the top of Exercise Detail (canvas frame 14 is authoritative for layout). Library list rows unchanged (no GIFs in lists — bandwidth + visual noise).

### 5. Parity
Add/verify `exercise-detail` capture in `ScreenshotTests` + `frame-map.json` → frame 14, so the parity report proves the layout.

## Security / RLS
Bucket write = service role only (import script); public read matches the soundboard bucket posture. No new RLS on `exercises` (global read, no client write — unchanged).

## Verification
- Unit tests (node:test): matching logic (slug normalization, name/equipment matching), pack-schema validation, idempotency skip logic.
- Import run evidence: counts (expanded / matched / downloaded / skipped / unmatched), then a SECOND run showing all-skips (idempotency).
- License finding recorded before mirroring.
- CI: `build-test` compiles `GSGifView`; `screenshots` captures Exercise Detail with a real GIF (seeded exercise); parity report row for frame 14.

## Non-goals
Video (GIF only); user-defined exercises (v2); Library search/filter overhaul; per-list-row thumbnails.
